# 本地新增与导入验证

## 选择一条编辑路径

- 本地改包：在本地生成节点和标识，通过浏览器或已授权导入入口上传候选，再验证结果。浏览器承担导入与验证，不先在线新增同一字段来取得标识。
- 在线设计器：用户选择直接在线编辑时，在设计器新增、保存并验证即可；无需再修改本地包。只有任务另需备份、版本管理或交付包时才导出。
- 不把两条路径串成“在线建字段取标识 → 本地再新增 → 再导入”的循环。已有未保存在线改动时先核对当前用户意图和状态，避免本地候选重复新增或覆盖。

## 本地构造

在可信原包的独立副本中新增字段、控件或其他已知结构。优先参考目标包的同类完整节点，结合同版本、同模型、同父容器的模板和知识确认属性、序列化与绑定。可复制结构，但需逐项处理身份、引用、业务属性和子节点，不能把模板实例原样复制后只改名称。按 [属性适用性](property-applicability.md) 保留缺省；不把样本交集当必填属性清单，不自动补 `MustInput`、`Lock` 或用 example 填默认值。

不要为了取得一个新标识先打开设计器、复制字段或让用户手工建字段。`generation.status=unverified` 表示平台内部生成机制未被验证，不表示本地候选禁止生成，也不要求复刻平台算法。

## 身份与关联

- `Key/Number` 等业务编码按命名、长度和作用域约束分配，并检查源码消费者；不是随机替换项。
- 新节点的独立 `Id/PkId` 按目标包已观察到的格式生成，并检查基线、祖先及候选内的冲突。仅在目标格式确为 UUID 时使用相应 UUID 格式；不把所有标识都当 UUID 或数据库主键。
- `MasterId/oid/ParentId/EntityId/FieldId` 等先判断是节点身份还是关联，按实际语义保留或映射。`oid` 若指向继承祖先，不可重生成；字段和控件的 Key 可以按绑定合同相同，不强加整个包全局唯一。
- 同时新增字段、控件、列表列、多语言或嵌套节点时，建立旧模板值到新节点值的映射，更新全部内部引用并检查外部引用；没有该节点或关联就不凭空补上。
- 特定对象若确实依赖服务器登记、序列分配或未公开序列化，记录具体依据，只暂停受影响节点，继续可完成的本地工作。

## 工具与验收

`metadata_author.py verify-candidate <knowledge> <baseline> <candidate> --contract <json>` 校验本地新增候选；合同记录 `candidate_provenance.classification=local-authored` 和实际模板/生成依据。详见 [内部描述](authoring-contract.md)。现有 `verify-platform-candidate` 保留平台导出血缘检查。

两个入口当前仅覆盖既有元数据单元内的完整节点新增，要求有效同环境知识及 `changes[]` 全为 `add`。`plan/apply` 的标量补丁器不负责自动构造新节点；遇到 `candidate-required` 应在本地生成候选再校验，不转去设计器。混合修改、新增单元/文件或脚本未覆盖的复杂结构采用任务内的本地生成与差异检查，保留原包和完整变更记录；不能将局部脚本通过当作整包验证通过。

本地检查包括 XML/包完整性、身份冲突、父容器、类型、字段/操作绑定、继承、语言和依赖差异。脚本检查不足或证据缺失时明确标出待验证项，不伪造知识库通过状态。

已有授权覆盖导入时，导入候选并核对逐文件结果、真实入口及用户要求的业务场景；失败先读具体错误，在本地修改受影响内容后再验证。只有错误或对象合同确证需平台生成时，才为该特殊对象选择平台创建；若在线保存已完成该对象修改，直接验证，只有本地剩余变更或交付需要时才导出合并，避免重复新增。成功达到任务验收条件后停止，不追加无关在线编辑或重复导入。

保留原包作为回滚源。失败后的候选可以继续修订，但始终与同一可信原包及累积差异对账，不冒充新的平台原始基线。静态通过不等于导入成功或运行验收通过。
