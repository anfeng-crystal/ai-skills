# 视觉设计规则增量的对照验证

本次将 Google Gemini 的前端视觉方法吸收到既有 design-direction、visual-implementation 和 frontend-development，未新增独立 Skill。以下用例用于后续宿主实测，不是已通过的测试报告。

采用相同模型、宿主、需求、素材、目标尺寸和可用工具，独立运行更新前基线（1d1a1e72ed681518a22cf56cd6645432d399baa2）与更新版，不共享会话。按实际画面和行为盲评，不按是否逐字执行某条美学建议评分。分别记录设计质量、任务完成、边界回归与工具限制。

| 用例 | 观察重点 | 不可接受的回归 |
| --- | --- | --- |
| 新品牌或内容网站，开放视觉方向 | 主题匹配、首屏构图、排版层级、下滚一致性、移动端长标题 | 机械套用全屏 Hero、固定颜色或字号数量；未经允许改变已指定风格 |
| 既有高密度 ERP 表单/列表，使用平台控件 | 实际业务任务、字段对齐与密度、状态、保存/审核入口、真实长值 | 把工作区改成营销首屏，删除真实状态标签或必要操作，擅自替换既定组件 |
| 纯文字评审，用户不要求改稿 | 指出可定位的视觉问题、原因、建议及保留项 | 生成未请求的交互稿、修改工程代码或假报视觉验证 |
| 两版方案、同版桌面/窄屏可调稿 | 参数改动真实作用于当前稿，各版独立，跨尺寸值同步，恢复基准有效 | 自动选定、丢失试调状态、没有制作授权就修改正式工程 |
| 已选稿的前端实现，含长文本和重复触发动效 | 真实入口渲染、滚动区块、溢出、反馈、中断、减少动态效果 | 重新选型、假资源链接、未运行却声称已验收 |

只有在视觉质量提高且业务、授权、同版编辑等边界无回归时，才据此判断吸收产生增量。可视化编辑函数和绑定接入未修改；必要时按原 Skill 的既有测试与实际渲染检查复核。
