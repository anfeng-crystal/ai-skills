# 元数据血缘门禁

## 为什么先判定血缘

输入文件存在、名称像原包、能解析或来自上一会话，都不能证明它是原始基线。历史 agent 修改包再次被当作基线，会把未经授权节点和错误身份继续传播；本 skill 必须在任何写入前阻断这一点。

## 每个文件记录

- 绝对路径和 SHA-256；
- 环境、平台版本、导出时间和导出人/方式；
- 导出类型、选中资源、安装目标与包产品版本；平台导出血缘本身不证明安装入口或跨版本兼容性；
- 直接父产物及其哈希；
- 是否经 agent、脚本、设计器保存、导入或重打包；
- 是否完成“导入—设计器打开保存—重新导出”对账；
- 证据来源，而不是推断。

合同只接受三种基线分类：

| classification | 资格 |
|---|---|
| `platform-exported` | 目标环境直接导出，有环境和时间证据 |
| `user-confirmed-original` | 用户明确确认未被 agent/脚本修改，并说明来源 |
| `repository-canonical` | 版本库规范源，有平台回导或发布血缘 |

`ai-derived`、`derived-candidate`、`unknown`、历史修复包和仅静态通过的包均不可作为新修改基线。用户明确指出某包是先前会话修改物时，立即把此前基于它作出的“原包”判断作废。

## 污染处理

若只有派生包：

1. 只运行 `inspect` 和只读差异分析；
2. 将差异标为 `approved-business/platform-generated/legacy-valid/agent-derived/unexplained`；
3. 不自动保留或删除 `agent-derived/unexplained`；
4. 取得可信导出，或由用户明确指定原始版本；
5. 重新生成合同，旧候选和旧批准不沿用。

“标准模板没有该节点”只证明它不是标准定义，不能单独证明业务节点应删除。删除还需用户授权、来源和引用检查。

## 写入边界

- 修改已有标量属性可以走精确字节补丁，但必须命中可信基线、唯一节点和实际合同。
- 新字段、控件、操作、规则、插件节点和多语言行必须由同版本平台生成身份；agent 只验证平台候选。
- 不复制标准模板或另一业务对象的 `Id/PkId/oid/Key/ParentId`。
- 不把继承节点完整物化到子层；恢复继承只移除真实差量覆盖。
- 本地候选、DEV/TEST 导入、生产导入和发布分别核对授权范围；同一条用户指令或同一已批准方案可以明确授权多个阶段。已覆盖阶段连续执行并验证，不逐阶段重复确认；未覆盖阶段先完成全部已授权准备，再询问。候选完成后返回主任务继续已授权工作，不以候选生成代替平台验证或整体完成。

## 平台导出与安装入口

官方[二开安装包制作](https://vip.kingdee.com/knowledge/specialDetail/218022218066869248?category=475348205593507584&id=43334364940533760&type=Knowledge&productLineId=29&lang=zh-CN)（更新于 2026-07-30，未标最低版本）区分补丁方式导出与普通导出：前者用于 MC 升级并有产品版本校验，后者用于开发者门户导入，不能据包扩展名混用安装入口。该说明只覆盖二开安装包，不可套到 DTS、工作流或单对象导出。记录目标版本、实际包类型和安装入口后再判定可用路径；本 skill 的离线候选、身份和授权门禁不因此改变。

## 验证层级

1. 静态：哈希、成员、XML、合同、精确差异；
2. 平台：导入、设计器重开保存、重新导出；
3. 运行：真实菜单/首页入口及业务场景；
4. 生产：发布、缓存、回归和回滚。

只完成前一层不能用后一层措辞。回滚源必须是可信发布前导出，不是本次来源不明输入。
