# 工作流参与人与审批节点行为

用于区分指定参与人、驳回目标参与人待定、会审节点加签、会签节点保留人工审批、驳回后重复审批人、参与人解析顺序、发起人与审批人相同处理，以及多种跳过/审批条件同时满足的情况。提交操作后的自动审核与流程寻址仍读 [提交与寻址合同](workflow-submit-audit.md)，不能借用其 V8/V9 版本规则解释本页机制。

## 指定参与人未生效

先区分指定动作发生在单据提交时，还是在前面的审批节点；两者需要核对的配置不同。官方对 V6.0.1 及以上版本给出的检查链如下：

| 场景 | 核对配置 |
|---|---|
| 单据提交时指定后面审批节点参与人 | 工作流服务系统参数 → 流程总体参数 → 提交节点参数 → 被指定节点的参与人范围 |
| 前面审批节点指定后面审批节点参与人 | 前面审批节点的指定后续参与人参数 → 被指定节点的参与人范围 |

“允许指定后续参与人”中的“后续节点”选项，官方明确仅支持苍穹 PC 端；这不等于所有指定参与人能力都只支持 PC。先核对客户端、当前动作及指定目标，不能把移动端缺少该选项直接当作权限或插件故障。

参数名、选项值和节点参与人范围按目标设计器与有效流程定义核验；上表是配置层次，不是 XML 属性或 Java API。来源未承诺改定义后会追溯改变在途实例，应同时核对实例采用的流程版本。只读诊断到配置和记录为止；已授权修改后，分别验证提交指定、审批中指定及实际客户端上的人员选择结果。

## 会审加签

- 官方知识库对 V6.0.1 及以上版本的说明是：会审节点支持前加签，不支持后加签。配置入口为“流程服务云 → 工作流服务 → 设计中心 → 流程设计”，选中目标会审节点，在“节点控制”中核对“允许加签”。
- 先区分目标是否确为会审节点、需求是前加签还是后加签，再查生效配置和当前任务状态。不要因未见后加签入口就按按钮权限故障修复，也不要由普通审批节点或 SDK 中存在加签方法推导会审支持后加签。
- 上述结论以来源标注范围为依据；目标版本另有明确合同或实际实现差异时按目标证据处理。仅勾选配置不能证明当前在途实例已采用该定义，需核对实例所用流程版本。

## 发起人与审批人相同

官方针对 V7.0.1 及以上版本给出的入口是：在流程设计画布空白处选择流程级“流程控制”，核对“审批人和业务发起人相同时处理方式控制”。它与单个会审节点的“允许加签”配置不同。

排查时核对实际业务发起人、解析出的审批人、目标节点及有效配置；不以创建人或当前登录人代替业务发起人。知识库短文未展开该配置在所有节点类型、已有实例和升级场景下的完整语义；需要改动时读取目标设计器选项及有效定义，不能凭中文标签猜 XML 属性、枚举值或 Java 开关。

### 会签节点需要保留人工审批

官方针对“会签节点不受发起人与审批人相同自动审批参数控制”的问答指出，该参数统一控制，不能直接为某个节点配置豁免。给出的替代配置是：关闭该参数，在仍需相同人员自动审批的普通审批节点中，按“流程控制 → 自动审批”配置“发起人=当前参与人”；需要人工审批的节点不配置这项自动审批条件。

这是一种调整配置范围的方案，先盘点受该参数影响的节点及已有条件，再核对哪些普通审批节点应保留自动审批。不能只关闭参数便认为其他节点行为保持不变，也不能把会签与会审视为同一节点类型。未配置此条件只说明不由这项条件触发自动审批，仍须检查其他跳过/自动审批条件。

该问答未标版本，也未细化“全局”是系统级还是流程级作用域；不要把它与上文 V7.0.1+ 的流程级选项无证据合并。修改前以目标参数作用域、有效流程定义及节点类型核实适用性，不凭标签猜 XML 属性或枚举值。

## 多个条件同时满足

官方另一篇问答列出的优先级由高至低为：

1. 跳过条件。
2. 业务申请人和审批人相同时审批。
3. 自动审批。
4. 重复审批人控制。

该问答未标适用版本，不将其当作所有版本通用的执行保证，也不套用相邻文章的版本号。把它作为逐项核对有效条件与执行记录的顺序线索；同时满足时，不只看排在后面的重复审批人配置。文章给出优先级，但没有完整说明短路、每种结果状态和所有节点例外，未核验时保留这些边界。

## 驳回目标参与人显示“待定”

对“驳回至已选节点时无法选择驳回参与人”的问题，先查是否存在多个同意决策项，以及流转线条件是否引用审批决策项。官方问答在这一场景下说明：同意与驳回使用同一套预计算/预测逻辑，决策项条件优先时可能使驳回无法预测；如果流转条件依审批决策判断，驳回决策项也需要有相应连线条件。

据此对照实际决策项、出口线条件、驳回目标及有效流程定义，检查驳回分支是否遗漏；“待定”本身不能证明用户、权限或目标参与人范围配置错误。来源未标版本，也未给完整预测算法、条件表达式或所有分支拓扑，不能直接补一条无条件线，或把这一原因推广到所有“待定”提示。

已授权修改时按业务决策补齐对应连线条件，保留原有同意分支；分别验证每个相关同意决策和驳回决策的实际去向、参与人预计算及最终任务记录。仅恢复人员选择框不等于路由正确；此处的目标预测问题与“驳回后重复审批人不自动审批”分开诊断。

## 驳回后重复审批人不自动审批

官方问答说明，重复审批人按驳回所走路线重新计算前序节点中的相同审批人；文中场景是在驳回节点前已经审批过的人员，驳回后重新提交回到驳回节点时不再被计算到。不要只凭整段历史中出现过该审批人，就认定当前节点必须按重复审批人自动审批。

先核对实际驳回节点、驳回目标、重新提交后的经过路线和各次审批记录，再检查当前生效的重复审批人配置及上文条件优先级。若业务明确要求该场景自动审批，官方给出的方向是另设自动审批条件；具体条件必须从业务要求和目标设计器能力确定，不能直接套用“发起人=当前参与人”或扩大到所有驳回路径。

该问答未标版本，未说明所有节点类型、驳回方式和历史记录的计算细节。将其作为路径相关的排查依据，不推广为“驳回后一律不自动审批”。已授权调整时，至少比较正常向前流转、实际驳回重提路线，以及同一/不同审批人的结果，并核对有效流程版本与任务记录。

## 参与人解析与显示顺序

审批参与人与配置显示顺序不一致时，先核对参与人条件。官方问答给出的条件执行顺序是“如果1、如果2、否则”；其中缺失条件的“如果”会被当作“否则”。因此先检查每条条件是否完整、实际命中哪条及解析出的人员，不能只调整显示顺序来修复条件缺失。该问答未标版本，也未说明多个条件同时命中、同一条件返回多人或串签的全部排序规则，不由此推断这些场景的执行合同。

需要实际解析依据时，官方“参与人解析过程”功能可查询**在途流程已经走过和当前节点**的解析过程：从“工作流服务 → 运维中心 → 参与人解析过程”，或“监控中心 → 流程实例 → 更多 → 查看参与人解析过程”进入，选择目标节点并看详情。记录目标实例、节点、有效定义、条件与解析结果，区分人员选择和页面显示。变更记录标明 V6.0.1 初始提供，V7.0.1 支持显示流程异常情况下的解析过程，并列有异常流程信息入口；仍核对目标版本和可见权限。该页没有承诺未经过节点、已结束历史流程或所有版本都可见，查询无记录不能单独证明未解析或人员配置错误。

## 变更与验证

沿用 [工作流与布局变更](workflow-metadata-change.md) 的生效定义、入口、授权及分层验收合同。只读排查不改流程；已授权修改时保留现有流程拓扑和其他节点配置。用相同/不同参与人及实际涉及的多个条件组合验证目标结果，核对任务、节点与审批记录，不把界面按钮出现、静态包通过或勾选成功当作流程运行通过。
