# MCP 工具发现、认证分层、参数与确认恢复

用于苍穹 MCP 客户端工具缺失、发现成功但业务调用失败、`inputSchema` 与接口文档不符，或敏感工具要求协议确认。先沿用入口的目标版本、凭据来源及请求授权规则；只给方案/模板时不发请求。以下账套级行为依据 V9.0.0，不能反推所有旧版本支持 MCP。已确认使用旧集群级 MCP 时，按其目标合同核验。

## 工具列表缺失

1. 核对实际服务类型、目标账套与当前客户端配置。V9 账套级工具发现请求头需有 `cosmic_mcp_token` 和 `erpAccountId`；缺账套可能得到空列表或仅部分非 API 工具，填错账套可能得到另一账套的工具。空列表不能单独证明 API 未部署或权限失效。
2. `erpAccountId` 是数据中心 ID，不是名称、组织 ID 或租户 ID。优先使用用户已指定的配置证据；在已授权页面范围内可核对第三方应用“更多 / 当前账套信息”。不为查 ID 自行扩大到 MC 或切换账号/账套。
3. 核对目标工具实际名称、关联 API、注册状态及本次发现结果。工具“已发布”不证明客户端已加载最新定义；“已下架/失败”不会在列表展示。注册状态与租户暴露范围审阅交 `kingdee-security-review`；普通工具发现不自动执行安全扫描。
4. 若需要已有 Monitor 日志，V9+ 关键词 `McpAccountTool`，已确认旧集群级服务用 `OpenApiMcpProvider`。仍按 `kingdee-observability` 的现有日志授权范围读取；不为刷新列表重置状态、下架或发布服务。

## 发现成功但业务调用失败

| 环节 | 认证/授权证据 | 不能直接推导的结论 |
| --- | --- | --- |
| 工具发现 | `cosmic_mcp_token`；V9 账套上下文 `erpAccountId` | 发现成功不证明业务 Token 或业务用户有操作权限 |
| 业务 API | 独立的 `access_token`，且与 `erpAccountId` 同账套 | 不能把发现 Token 作为业务 Token；不能把 `getToken` 响应当成 MCP Token |
| API 与业务权限 | 第三方应用对关联 API 的访问权限、Token 对应业务用户的权限 | 工具可见或应用获授权不等于单据/模块操作获授权 |

使用当前端点的脱敏错误定位环节：FAQ 中 401 常见于 Token 缺失/过期，403 常见于第三方应用 API 权限不足；它们不是唯一根因。FAQ 还列出代理丢弃带下划线请求头可能引起 `-32001 / Unauthorized MCP access` 或 401。先核实本次请求、路由及代理配置证据，不因错误码自动修改 Nginx、重启或替换请求头。

来源没有给出完整的 MCP Token 换取端点、请求体与双层交换协议。缺合同时明确待确认，继续独立参数/状态核验；不发明鉴权路径。业务 Token 取得与到期管理仍以目标实际认证模式及返回值为准；不以 FAQ 的“两小时”覆盖增强型 Token 的 `expires_in` 剩余毫秒合同。直接 API 验证也受原有调用范围限制，写接口不能作为默认探针。

## `inputSchema` 不一致

- 同时取得当前工具返回的 `inputSchema`、目标 API 契约及是否存在历史已保存 YAML 的证据；工具名称可修改，不从名称反推接口路径或参数。
- V9 新服务不再保存原始 YAML，API 参数通常由 API 契约生成；兼容历史服务时，已有 YAML 优先，无 YAML 才读 API 契约。因此仅更新 API 文档不能证明历史工具参数已同步。
- 逐项对照实际字段名、类型、必填项、嵌套结构和业务含义，特别留意 `$key`、`$value` 等虚参数。不要自动填入猜测值或强制套用 kapi 的 `data` 包装。
- 历史 YAML 与 API 契约不一致时先给差异及影响，保留历史数据。清除 YAML 会切换参数来源，属于单独变更；经相应授权完成对齐后才可清理，再核验网关实际 `inputSchema`。等待扫描或看到“待更新”都不是生效证明。

## `MCP_CONFIRMATION_REQUIRED` 确认恢复

FAQ 3.3 说明，标记 `sensitive` 的工具首次调用可能返回 `MCP_CONFIRMATION_REQUIRED` 和 `confirmationToken`；二次调用同一工具时，令牌放在 `params._meta["bos.mcp.confirmationToken"]`。这是请求协议元数据，不能替换 `cosmic_mcp_token` / `access_token`，也不能作为业务 `data` 字段或猜测新增的工具参数。

1. 先核对本次返回码、目标环境/账套、工具和业务参数。收到令牌不代表用户授权或业务执行成功；沿用已有明确动作授权，若宿主要求当次确认则先完成该确认，不因协议恢复扩大范围。
2. 授权与必要确认齐备后，按当前客户端实际支持的 MCP 协议入口带回返回的令牌，保持同一工具及获准业务参数；提交/保存类仍沿用原逻辑操作的幂等键与目标防重合同。客户端不能表达该 `_meta` 时，先确认原生 MCP 调用能力，不把令牌塞进不支持的参数，也不改走直连写 API 绕过确认。
3. 完成一次确认调用后，按返回结果判断。若仍要求确认、令牌缺失或失效，停止这条自动写入重试链，保留脱敏错误并核查实际协议/网关日志。超时或结果不明先在获准只读范围核实业务状态，不能自动再次执行。用户取消或授权范围变化时不继续旧调用。

来源未给出令牌寿命、动作绑定、重放或失效细则；不自定 TTL、不跨工具/账套/业务参数复用。确认令牌按秘密值处理，只保留当前获准调用所需内容，不写入日志或交付示例。交付分别记录“要求确认、是否已重调、业务结果是否证实”，不能把没有再次弹出确认当作操作成功。

交付只报告工具发现、业务调用、参数核验和确认恢复各自是否执行及结果，保留注册/版本/协议缺口，隐藏真实 Token、账套和地址。
