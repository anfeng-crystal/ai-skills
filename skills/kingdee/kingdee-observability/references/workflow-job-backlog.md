# 工作流停滞与 Job 积压

在单据流程长时间停滞、Job 消费不及时或已观察到工作流待消费记录时按需读取。全局 Job 积压只说明全局待消费状态，不能直接证明某张单据停滞的根因。

## 最小诊断顺序

1. **命名单据先查记录存在性。** 转 `kingdee-sql-and-data`，依据目标环境的实际表结构和业务关联键，分别报告该单据的活动流程、历史流程是否存在。只有业务状态文字不足以证明流程已创建；活动和历史记录均不存在，也不足以单独判定未启动的原因。仅有离线日志或无数据库授权时先分析已有资料，将记录存在性列为证据缺口，不自行联网或扩大范围。
2. **有消费延迟线索再查积压。** 数据库读取必须有独立、精确的只读范围：环境、数据库/表、谓词、聚合或结果上限、超时/负载边界。已有授权覆盖时沿用，不逐步重复确认；日志查询的时间窗或审批引用不能替代数据库授权。先核对目标版本中的字段与状态语义，再决定是否使用下述来源示例。
3. **区分积压快照与消费停滞。** 官方文章用 `t_wf_jobrecord` 中 `fstate='created'` 的数量观察待消费积压：

   ```sql
   select count(1) from t_wf_jobrecord where fstate='created';
   ```

   这是全表聚合的来源示例，只有授权范围包含它时才可执行；不能因返回一行就认定查询负载小。文章中的数千、数万是案例规模，不是告警阈值。单次数量不能说明消费是否停止；需要在已有范围内结合前后快照、调度执行线程或引擎日志。缺少单据与 Job 的关联证据时，只报告全局积压及其与该单据的关联尚未确认。
4. **按证据收束或升级。** 在相应只读范围内，通过调度中心的“执行服务器监控”观察相关执行线程，并结合积压变化判断消费情况；线程出现本身不证明已消化积压。仍无法解释时，补充经授权的工作流引擎日志与同时间段证据。输出已证实事实、诊断推断及最小证据缺口，不由单一症状推出根因。
