# 苍穹问题原因分析参考

## 适用场景
- 生产或研发环境故障排查。
- 性能瓶颈、内存、线程、数据库连接池、缓存、部署发布问题。
- 代码缺陷、配置差异、依赖版本变化导致的异常。

## 排查流程
1. 定义问题：现象、影响范围、发生时间、触发条件、最近变更。
2. 收集证据：应用日志、平台日志、监控指标、告警、git 变更、配置差异。
3. 建立时间线：把日志、监控、发布、操作记录按时间对齐。
4. 提出假设：代码缺陷、配置问题、资源耗尽、依赖故障、数据问题。
5. 验证假设：复现、查日志证据、对比正常环境、最小化验证。
6. 输出结论：直接原因、根本原因、止血方案、根治方案、验证步骤、预防措施。

## 常用证据方向
- 日志关键字：`ERROR`、`Exception`、`Timeout`、`OOMKilled`、`Connection pool`、`deadlock`。
- JVM：线程 dump、GC 日志、堆 dump、CPU/内存趋势。
- 数据库：慢查询、连接池、索引、锁等待、事务边界。
- 苍穹二开：插件事件时机、跨库事务、DataSet 生命周期、字段标识、元数据配置。

## 列表或页面无数据
- 先还原用户实际入口：URL 参数、`formId`、`billFormId`、移动/PC 页面类型、登录用户、角色和组织。
- 优先追踪过滤链路，不要把并发出现的远程调用超时、Dubbo 本地调试超时或后台异步错误直接当成无数据根因。
- 按顺序核对过滤来源：页面/列表元数据默认过滤、用户常用/方案过滤、URL 参数插件、列表插件 `setFilter`、平台查看权限、组织维度权限、数据权限和操作规则。
- 涉及权限时，必须区分“角色有菜单/操作权限”和“最终查询 QFilter 有数据”；查看权限、组织维度、数据权限和操作规则会被平台组合后注入 ORM 查询。
- 需要给出 SQL 证据时，围绕同一个 traceId 展示过滤配置查询、权限/操作规则查询和最终业务表 SQL；若日志因长 `IN` 条件截断，明确说明可见部分和不可见尾部。
- 若 SQL 出现 `1!=1`、空 `IN` 或恒假条件，先查上游 QFilter 来源和空集合生成点；不要只从结果 SQL 反推某个业务插件生效。

## 列表/F7过滤条件归属

列表或 F7 漏行、多行、搜索不可见时，先固定实际入口、目标实体、问题账号及组织、应可见/不可见的样例和当前过滤方案。菜单/角色权限、同表单据存在、管理员可见都不能单独解释问题账号的数据范围。

当前官方方法适用于 V5.0.12+：实体运行监控的“方法执行监听”使用类型 `list`、方法 `BillList.generalFilterParameter`；在获准复现范围内刷新目标列表后，查看 `list.BillList.generalFilterParameter` 行。先分析已有导出；新采集的当前账号限制、启停与授权边界沿用 `kingdee-observability` 的[实体监控卡](../../../kingdee-observability/references/entity-runtime-monitor.md)，由已授权执行工具实施。社区中的增授权限、清除或复制权限是另外的变更，不能作为诊断默认步骤。

| 实际日志字段 | 定位用途 |
| --- | --- |
| `FilterParameter.filters`、`ClientQueryFilterParameter.filters`、`myQFilters` | 对照本次请求进入过滤链的条件；不从名称或一条样例推断所有版本的最终合并顺序 |
| `MainOrgQFilter` → `MainOrgQFilter.after` | 主业务组织/功能权限组织隔离条件，比较插件执行前后是否变化 |
| `SpecialDataPermQFilter` → `SpecialDataPermQFilter.after` | 特殊数据权限条件，比较插件执行前后是否变化 |
| `DataPermQFilters` → `DataPermQFilters.after` | 数据规则条件，比较插件执行前后是否变化 |
| `PlugCustom.filter.1`、`PlugCustom.filter.2` | 业务或二开插件主动设置的过滤，进一步关联实际挂载与代码来源 |
| `BasedataCoreQFilters` | 基础资料自定义控制器的过滤条件 |
| `PlugCustom.orderBy` | 排序；不能仅凭此字段判定缺行、多行的过滤根因 |

先找哪条条件排除或放入了目标样例，再沿字段归属定位配置或插件。权限字段的 `.after` 不同于前值时，先核查插件对条件的修改；字段名属于权限侧不证明根因一定是平台权限。`null` / `[]` 仅描述本次该项输出，不能证明用户不受其他权限或过滤限制；缺少字段、日志截断、缺前后任一侧时保留证据缺口，不填造对比值。上述监控输出不是最终 SQL；需要 SQL 时仍按上节关联同一请求证据。

复现应优先保持问题账号及上下文。把账号 B 的权限复制给 A，也不能保证复现 B：如“创建人=当前用户”等动态条件会随账号变化；仅替身可见或不可见不能关闭原问题。F7 还需核对调用方传入过滤及实际打开的目标，不能拿同实体普通列表结果替代 F7 证据。确需修改过滤时先给具体条件及业务影响，再按任务授权实施，不以去掉权限过滤作为默认修复。

输出条件归属、前后差异、受影响样例的脱敏判断，以及已证实/待证实的配置或插件来源。保持日志值和账号信息脱敏；未复现、未取得最终查询或未核对目标版本时分别说明。

来源：[如何排查单据列表或F7数据行不准确的问题](https://vip.kingdee.com/knowledge/769596461381780992)，更新 2026-07-31 10:58，正文标明 V5.0.12+（V6+ 有菜单）；以目标实际输出为准。

## 列表总数与可见行不一致

先区分当前页行数、列表总数、去重后的单据数和导出行数，固定同账号、组织及过滤方案下的样例；分页本身就会使当前页行数小于总数。只有口径对齐后仍不一致，才定位实际取数器、取行与计数的查询证据。

- `IdQuery`：官方排查文档指出取行会去重，而计数可能未去重。检查主表与分录、多语言表的关联基数，确认同一主键是否由关联产生多条记录；不能仅因总数偏大认定权限漏行，也不直接补 `DISTINCT` 或删除数据。
- `SqlQuery` 自定义取数：核对实际数据提供者及其 `getRealCount` 实现，确认取行与计数使用一致的过滤、关联和去重口径。只替换取行逻辑可能留下旧计数；方法签名和扩展点按目标依赖确认，不套用另一版本实现。
- F7 下拉模糊匹配、弹窗与普通列表分别保留请求及结果证据。它们可能走不同过滤或去重路径；一处结果正确不能证明另一处正确，过滤归属仍按上一节核查。
- 达到列表上限时，核对目标单据的最大条数参数。来源文档描述的 10 万条限制涉及列表及“选择全部”，不等于导出上限；需核对目标版本与实际配置，不能用该数值截断导出或据此宣布数据丢失。

输出明确的计数口径、取数模式、样例主键的重复来源及取行/计数差异。没有计数查询或数据提供者证据时保留未知；诊断不授权调整上限、过滤、权限或业务数据。
