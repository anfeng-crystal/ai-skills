# 原生对照与导出

## 在设计器里复现差异

1. 保留可信原包、本地候选和已有的原生导出。先记录目标环境、页面编码、模型、字段类型、放置容器及继承状态。
2. 同一设计器会话里，先取现有字段的目标属性，再通过控件库新增同类型、同层级的临时字段。对照拖入后的默认值、设置标识和名称后的实体字段与表单控件、父容器和控件顺序。选择项同时比较显示文本与存储值。只取证的临时编辑在完成后撤销，验证样本消失；需要保存取证时使用已授权的隔离对象或环境。
3. 对比具体属性栏和节点属性。区分名称文本、属性编辑器及其提示、实体字段绑定、标准字段库引用这四项。以编辑器真实输入和保存 XML 为据，不根据截图猜关联。若仍要归因给环境，需读到实际生效的编辑器分支或设置，并能解释同环境对照与跨环境观察。不要为消除提示擅自关联标准字段库。
4. 做原包、候选和平台原生导出三方差异。逐项核对缺省与显式值、布局顺序、父容器、标识引用、多语言及页面行为。将每项差异标为业务变更、平台保存生成或尚待解释。选择与实际需求一致的配置，去掉无业务依据的附加限制。

## 下拉字段对照示例

- 从控件库拖入普通下拉列表后，设计器分别生成实体里的 `ComboField` 与表单里的 `FieldAp`。用 `Key` 定位两者，核对控件的 `FieldId` 与实体节点身份相连，以及 `ParentId`、`Index` 是否与目标容器和位置一致。改名或改 `Key` 后再读两份 XML。已实测该流程会同步两份 XML 的业务 `Key` 和 `Name`，原绑定身份保持稳定，已生成的 `FieldName` 不会因 `Key` 改名自动更新，须单独按目标列名核对。
- 名称旁的「未引用标准字段」对应标准字段库的 `RefField`，表单控件绑定则走 `FieldId`。DEV 和生产均实测过从控件库拖入同类型下拉列表。两份 XML 都可保持无 `RefField`，图标仍随设计器生效的引用编辑器分支而异。同类差异先比对同环境原生新增，再查具体编辑器分支。字段未引用标准字段库时，不补造 `RefField`。
- 同类原生字段默认值以实际 XML 为准。生成的新增控件有容器内 `Index`。放进已有隐藏容器时先核实容器是否已满足要求，避免额外写字段级 `Invisible`；不从旧字段顺带复制 `Copyable`、`ShowClearBtn` 等与当前需求无关的限制。

## 移动原生控件排查

- 设计器画布显示工具栏、运行预览却缺失时，先查生效的移动列表模型和原生装载入口。针对按固定标识读取容器的平台实现，确认查找的是 `Key` 还是 `Id`，并核对子项的 `ParentId`、原生操作及状态权限。以同版本原生实例或运行代码确认合同，避免只改显示名称或 `Key` 后反复试包。
- 移动端复用 PC 上已有的附件等业务字段时，先确认原控件绑定的 `FieldId`，并核对新控件的移动模型、原生上传能力与父页签。业务附件与审批预览文件可能同属附件类型，须按绑定和用途确认。页签顺序与跨端附件回显通过原生预览验证。

## 核对可追溯的正式交付

- 离线候选按[修改审计属性](provenance-and-authoring.md#修改审计属性)更新修改人、修改时间和相应版本，记录的是离线修订时间。
- 需要平台保存记录且已获授权时，完成平台保存、重新打开并从设计器或开发平台导出。核对已有的修改人属性、实体与表单的 `ModifyDate`、`Version`、包版本和语言侧文件属于同次保存，核对平台生成的新字段和控件身份及 `FieldId` 等引用。用户已保存的原生导出通过差异核对后可直接交付，保留平台实际保存信息与语言关联。
- 按静态、导入、设计器预览和业务验收分别报告实际完成的阶段。已有成功导入和适用预览证据的本地包可交付。涉及原生保存产物时，文件系统修改时间不能代替平台保存历史。现有新增验证器若将原生保存更新的外层版本或语言关联报为其他结构差异，逐路径核对平台实际导出的差异和关联，保留新包的真实时间与关联值。
