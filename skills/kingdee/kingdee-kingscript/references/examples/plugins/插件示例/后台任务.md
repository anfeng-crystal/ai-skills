# 后台任务插件（AbstractTask）

## 入口与适用范围

调度任务继承 `@cosmic/bos-core/kd/bos/schedule/executor` 的 `AbstractTask`，实现 `execute(context: RequestContext, params: Map)`。这里的 `Map` 来自 `@cosmic/bos-script/java/util`，不是 JavaScript 原生 `Map`；事件参数保留声明类型，不改成 `any`。

新建空骨架可使用[后台任务模板](../../../templates/task-plugin-template.md)。下面展示业务参数的传入边界；不包含真实保存、消息发送或价格更新实现。

```typescript
/**
 * 调度任务最小入口。只展示已核验的参数读取，不执行真实业务。
 * 日志、进度、断点与重试语义须在目标项目确认后实现。
 */
import { AbstractTask } from "@cosmic/bos-core/kd/bos/schedule/executor";
import { RequestContext } from "@cosmic/bos-core/kd/bos/context";
import { Map } from "@cosmic/bos-script/java/util";

class ScheduledBusinessTask extends AbstractTask {
  /**
   * context 由调度框架传入；params 是 Java Map 桥接，键由调用方约定。
   * 以下键是业务参数示意，不是平台内置参数；缺值、类型与权限须在实施时校验。
   */
  execute(context: RequestContext, params: Map): void {
    let businessId = params.get("businessId");
    let executionId = params.get("executionId");
    let checkpointId = params.get("checkpointId");
    // 在此接入已验证的业务查询、日志、进度与断点服务。
    // 执行记录须区分成功、失败和中止，不能只在入口写入后永久保留 running。
    // 恢复时使用稳定业务键及幂等策略，不能把可变查询的数组索引视作可靠断点。
  }
}

let plugin = new ScheduledBusinessTask();
export { plugin };

```

`Map.get` 在脚本声明中返回通用值。业务键、值类型、缺值处理、数据范围和权限需要在具体实现中校验；`executionId` 是调用双方约定的业务执行记录键，不能当成框架自动注入的任务 ID。

## 调度方法与脚本可见性

下表来自已核验的 7.0 调度构件内嵌脚本声明：`AbstractTask` 的声明继承 `Task`。目标版本不同时仍应读取对应声明，不能把 Java public/protected 方法全部当作脚本可调用方法。

| 方法 | 脚本声明与使用边界 |
|---|---|
| `execute(context: RequestContext, params: Map): void` | 任务执行入口；setter 和 `stop` 不能代替它。 |
| `setTaskId(id: string): void` | 传入任务 ID；声明本身不证明可将保存业务记录放在这里，也不保证每次重试得到不同 ID。 |
| `setMessageHandle?(messageHandler: MessageHandler): void` | `Task` 声明中的可选方法；是否注入及调用时机须结合目标运行合同。 |
| `getMessageHandle?(): MessageHandler` | `Task` 声明中的可选方法；与 Java `AbstractTask.getMessageHandler()` 名称不同，不能自动改名后宣称脚本可运行。 |
| `stop(): void` | 官方说明为主动停止当前任务并抛异常中断程序；不是通用资源释放函数。 |
| `isSupportReSchedule?(): boolean` | 可选的重新调度支持能力；是否开启需先核对任务是否可安全重复执行。 |

已核验声明没有 `getTaskId()`、`getMessageHandler()`，`MessageHandler` 也没有 `sendMessage()`。不要以 `any` 绕过这些缺口，或从 Java 同名类补造脚本调用。`MessageHandler.handle` 是消息处理合同，不等同于向用户发送通知或上报进度；进度、通知需要目标版本真实接口依据。

## 业务场景与实施要求

下列场景可以沿用同一个明确类型的入口，并复用项目已有任务、日志、同步及通知服务。它们是业务实现要求，不是未核验平台方法的替代名称。

| 场景 | 输入、处理与结果 |
|---|---|
| 库存盘点执行日志 | 限定启用仓库和盘点范围，使用明确的执行记录关联键；记录开始、结束、失败/中止状态、处理数量及错误信息。重入判断还需可靠的幂等合同，不能仅查询一条 `running` 记录就宣称防重。 |
| 供应商与物料同步进度 | 从上次成功同步水位继续，保留供应商、物料两个处理阶段；仅在对应批次成功后推进水位，处理部分失败、重试和幂等。按阶段上报进度，具体上报接口先查脚本声明。 |
| 批量生成对账单 | 原示例口径是启用供应商、指定期间内已审核采购入库单的分录金额；沿用时确认实际实体、字段与期间边界。金额用已确认导入的 `BigDecimal`，区分空值与零值，保留成功/失败计数及重复单据处理。保存返回结果、失败明细和通知接口均按目标合同处理，不能只把未抛异常视为全部成功。 |
| 价格更新与断点恢复 | 原示例选择启用物料，取生效日期不晚于执行时点的调价记录，并按生效日期倒序取最近价格；沿用时确认实际字段、同日多记录的选择和价格回写合同。保留已处理进度和完成/中止状态。断点用稳定业务键或固定批次快照，不能依赖可能增删重排的查询数组下标；价格提交与断点更新要保证可恢复、可幂等。中断通知需明确接收人并核对真实发送接口。 |

## 停止、恢复与验证

- `stop()` 会中断当前执行路径；不要把 `super.stop()` 当作“正常返回后继续”的清理函数，不要笼统捕获停止异常后继续下一批业务。资源清理与断点记录应有自身的异常处理及一致性设计。
- 官方的主动停止说明不证明外部停止按钮、超时或其他线程会自动调用某个重写方法；这些时序和任务实例状态须按目标运行机制验证，不自行推断共享标志位可以跨线程生效。
- 本地静态检查应确认导入、`execute` 参数和所用方法的脚本可见性。调度注册、重复触发、停止、恢复、业务写入和消息发送属于运行验证，按目标环境及任务授权执行。
