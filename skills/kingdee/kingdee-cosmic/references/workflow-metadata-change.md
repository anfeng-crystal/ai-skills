# 工作流与布局元数据变更

用于审核计划、修改或交付 Cosmic 工作流、审批布局、业务布局和列表布局。先由 `kingdee-metadata-analyzer` 给出目标环境的实体/页面/挂载证据，再进入实现。

## 基线矩阵

每个业务入口分别记录：实体编码/FID、物理表、表单布局、列表布局、审批布局、菜单入口、插件挂载、当前流程定义和导出来源。以下事实不能互相推出：

- 共用物理表不等于同一元数据实体、同一布局或同一菜单入口。
- 表单布局存在不等于列表布局已覆盖；列表列、按钮、过滤和列表插件必须单独盘点。
- `inventory.json` 或文件清单存在不等于字段/页面/插件完整；有截断、warning 或只扫描根节点时必须回读原始 XML/设计数据。
- 导入成功、包结构通过或 Java 编译通过不等于目标页面已挂载和运行。

## 流程定义

- 提交后自动审核、连续提交/审核或“流程中流转”提示，按需读 [提交与寻址合同](workflow-submit-audit.md)，先区分目标版本、升级来源和异步寻址状态，再决定是否需要修改流程。
- 指定参与人未生效、驳回目标参与人待定、会审前/后加签、会签保留人工审批、驳回后重复审批人、参与人解析/显示顺序、发起人与审批人相同或多个跳过条件相互影响时，按需读 [参与人与节点行为](workflow-participant-behavior.md)，区分节点级、流程级配置及各来源版本范围。
- 流程任务主题的长日期显示缺时分秒时，读 [任务主题日期显示](workflow-task-subject.md)，先区分源值与格式化，并核对目标版本。
- 以目标平台当前发布后导出的 `.scheme` 作为生效定义基线。普通 `.process` 只能作设计参考，除非目标环境证据证明它就是当前待发布定义。
- 保留目标 `.scheme` 已证实的业务拓扑、状态机和正式提交/重提入口；不得绕过当前正式入口另造快捷链路，除非用户明确批准改变业务流程。
- 新增、驳回重提、撤回、终止和再次发起分别列来源态、目标态、允许入口和互斥条件；不能用一条“补状态”分支覆盖所有生命周期。
- 审批人为空、消息通知、渠道失败与重试只使用目标平台已证实的配置点或 SDK。没有 Scheme、SDK 或页面证据时写“待平台配置验证”，不得发明插件名、台账或重试机制。

## 字段编辑优先级

- 原节点已有的单字段可编辑/必录配置默认保留；除非用户明确授权删除，并已证明新规则完全覆盖。
- 审批布局的提交/审核锁定是默认边界；当节点配置了可编辑/必录字段时，节点例外必须能覆盖该锁定。界面规则关闭修改态后，仍要用真实审批节点验证节点例外是否生效。
- 不从另一个实体或布局复制控件 ID、字段白名单或插件绑定；先按当前目标实体/布局重建对应关系。

## 创建、打包与验证

1. 计划阶段必须覆盖表单布局、列表布局、审批布局、菜单和工作流，不只列字段和流程图；所有新 key 先按目标平台长度/冲突证据校验。
2. 新增布局/流程等对象交 `kingdee-metadata-change`，优先基于可信同类骨架在本地生成候选，检查新标识及关联后按授权导入验证；只有缺少可用结构依据或确证需服务器登记/分配身份时，才最小化平台采样。不能仅因没有现成 FID 就要求用户先在平台创建。
3. 元数据、流程、代码和说明按可独立导入/回滚的类别分包；失败候选不能混入最终交付目录。
4. 验证分层报告：ZIP/XML 静态结构 → Java 编译/测试 → DEV 导入/部署状态 → 目标环境真实菜单/首页入口页面行为。开发平台预览不替代业务首页入口。
5. 只有实际页面打开、流程发起/驳回/撤回/终止或用户指定场景通过，才能报告运行验证通过；未验证项必须保留。
