# Implement Feature

> Cross-platform Agent Skill: keep shell examples POSIX-friendly where possible, avoid host-specific paths unless provided by the user, and preserve user worktree changes.

## 触发
- 用户要求新增能力、补充业务逻辑、扩展接口、增加配置、改造流程或改变预期行为时使用。
- 只解释代码用 `explain-code`；只审查风险且不落地用 `review-code`；现有行为出错、回归或测试失败用 `fix-bug`；只要方案或审核用 `plan-decision`。
- 混合请求中同时包含“先方案”和“直接实现”时，先给最小方案和影响范围；用户明确要求直接改且范围局部时，可边实现边说明关键假设。

## 契约
- 目标、非目标、输入输出、影响面、兼容约束和验收方式必须清楚。
- 实现优先复用现有结构、服务、helper、wrapper、模板、脚手架、SDK 封装、成熟三方库和标准服务。
- 只有现有能力都不能满足时才新增抽象、方法或依赖，并说明缺口、影响和最小新增范围。
- 局部单点需求默认原地修改；新增共享层、helper 或兜底链路必须服务于当前需求，而不是未来可能复用。
- 方案阶段不声称已实现；实现后必须区分已验证和未验证内容。

## 工作流
1. 明确目标：确认使用者、输入输出、状态变化、影响对象、权限/兼容边界、验收方式和禁止改动范围。
2. 读近似实现：先查同模块、同类型能力、扩展点、命名、错误处理、测试、配置/schema、调用方和平台约束。
3. 盘点现成能力：按 helper、wrapper、模板、脚手架、SDK/框架内建能力、成熟三方库、标准服务和既有扩展点的顺序判断能否复用。
4. 给实施方案：用 3-5 点说明落点、改动范围、关键数据流、失败边界、兼容影响和验证方式；复杂或跨模块计划必须每阶段可独立验收。
5. 方案门禁：默认等用户确认后编码。已审核方案执行前只做 drift check，核对当前文件、配置、依赖、元数据、分支状态或外部状态是否仍匹配。
6. 编码前做最小范围自检：目标文件、新增文件、公共接口、抽象层、额外兜底链路是否都能由当前需求解释。
7. 实施改动：只改目标路径；新增配置检查 schema、解析逻辑、默认值和文档；新增 API 检查路由、权限、日志、错误码；新增参数/字段检查生产端、解析端、消费端和关键回调链路。
8. 验证闭环：优先跑目标测试、相关测试、构建、脚本或样例；无法执行时说明失败原因、替代验证和未覆盖行为。

## 门禁
- 需求缺少关键输入输出、验收口径、权限/兼容边界或数据模型时，先列关键假设；高风险假设必须确认。
- 改公共 API、数据结构、依赖、部署配置、权限模型或跨模块契约前，先说明影响和回滚/验证方式。
- 能通过配置、现有服务或既有扩展点完成时，不新增抽象或依赖。
- 单文件或单使用点改动不默认抽 helper；只有当前复杂度、重复调用或既有架构边界要求时才新增。
- 新增共享 helper、wrapper、模板层或三方依赖前，说明为什么现有能力和扩展点都不适用；影响公共层或调用方时先确认。
- 发现本质是 bug 修复时切换到 `fix-bug` 的根因闭环，不把回归修复包装成新功能。
- 不把任务过程、沟通记录或交付口径写入代码注释、skills、操作说明或示例说明。
- 不用顺手优化扩大行为面；性能、结构或样式调整必须服务于当前需求。

## 注释
- 新文件、模块、类、公共函数、公共接口、复杂私有函数、工具函数、关键算法、业务规则、事务/并发/异步/资源管理、异常边界和外部系统交互必须有稳定注释或语言原生 docstring。
- 注释写职责、输入输出、边界、副作用和长期原因；不机械复述代码表面行为。
- 简单局部语句不逐行注释；没有注释会让新增代码难以判断职责时，补模块/函数/关键分支级注释。
