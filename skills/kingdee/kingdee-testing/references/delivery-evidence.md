# 构建、测试与交付证据

用于 Gradle、包、DEV 部署、本地启动和 Git 交接。按任务所需层次取证，不把所有层次设为每次任务的必做项。

## 资产与构建

- 生成前标记 `task-local` 或 `formal`。用户明确要测试源码，或产品修复确需长期回归且项目策略支持，才是 formal；一次性测试、脚本、夹具、数据和 harness 为 task-local，优先放临时/隔离目录。不能为了保留临时文件临时改归属；未交付正式回归则如实说明。
- 从向上发现的 Gradle 聚合根/wrapper 运行明确模块任务，核对 SDK 和 JDK。compile、测试数量、静态检查和包内容分别记录；`SUCCESS` 是命令状态，`test NO-SOURCE` 是 0 个测试，不能称测试通过。
- mock/桩只能证明其设定条件内的逻辑；事件输入应有独立平台证据，不能据成功编译或人为注入值声称客户端/运行兼容。
- 打包和 Git 交接前，对比本轮创建清单、工作区、暂存区和包成员。清理可归因的 task-local 源码及生成类/JAR/ZIP 成员，保留既有或归因不明资产；发现临时资产进入交付包或待推送提交时先修正。暂存范围不等于全模块打包范围。

## 配套部署

- 元数据与插件字段/类型同时变化时，核对配套版本及导入/部署顺序；本地新代码不能证明目标插件已更新。用户自己导入时，收到结果后再推进依赖步骤。
- 并行脏文件须核对真实打包范围，不能因仅暂存目标文件就默认部署包已隔离。项目允许按已部署包替换目标类时，须含必要内部类并校验未改成员及回滚；不强推此方式给其他项目。
- 上传/重启返回只证明请求被接受。按项目合同核实目标服务状态、实例数和重启时间；如要求 `status=2`、`run_count=desired_count`、`lstime` 更新则逐项核实。
- 服务恢复与业务验收分开。代理获授权做页面验收时从真实菜单/父页核对 formId、布局、挂载和业务结果，开发平台预览不能替代；用户自己测试时到环境就绪交接，不能因本卡要求验收而接管页面或业务保存。

## 本地就绪与用户验收

用户要求“启动环境，我来测试”时，执行已授权启动，确认进程、端口及项目 `platform_ready`/等价标记；只有任务明确包含登录或打开页面时才完成这些步骤。条件未满足报告 `not_started`/`not_ready`，满足后交付地址和版本，页面及写入验收留给用户。

用户报告通过后记录其验收范围和对应版本；不要冒称代理运行，也不把有效用户确认退回待验证。后续改动只重核受影响的证据。

## Git 与完成状态

Git 提交说明按完整业务结果和最新确认语义命名；功能开发中的纠错不自动把提交归类为修复。仅检查获授权范围，不为改说明擅自改写已推送历史。正式测试按既有项目体系交付，task-local 文件不进入 Git；不靠文件名或目录猜测清理。

| 状态 | 必须有的证据 |
| --- | --- |
| `compiled` | 目标类路径编译成功 |
| `tests_passed` / `test_no_source` | 实际执行用例及结果 / 无测试执行 |
| `package_verified` | 成员、范围和摘要已核对 |
| `restart_requested` / `service_recovered` | 请求已接受 / 状态、实例数和时间满足合同 |
| `runtime_verified` | 代理在授权范围实际验证真实入口和指定场景 |
| `local_ready_for_user` | 进程、端口、平台就绪及任务明确要求的登录/页面已完成 |
| `user_acceptance_passed` | 用户确认的场景、版本和结果；不等同代理实测 |

只报告已达到的状态及实质缺口，不用低一层结果替代高一层结论。
