# Cosmic 错误诊断与代码复核模式

## 诊断分类

| 现象 | 首要证据 | 动作 | 停止条件 |
|---|---|---|---|
| 插件未触发 | 实体/页面/操作挂载、派生页面、插件类型 | 用元数据分析器还原真实入口和继承链 | 只找到类、未确认挂载时不能判定代码无效 |
| `ClassNotFound` / `NoClassDefFoundError` | 模块依赖、部署包、目标版本 classpath | 对比 Gradle 依赖与运行节点部署资产 | 未确认目标版本时不建议换包名或抄社区类名 |
| `NoSuchMethodError` / override 失败 | 当前项目 JAR/Javadoc、完整事件签名 | 用 `kingdee-sdk-helper` 和编译结果核对 | 仅有社区示例时标为候选，不宣称签名成立 |
| 字段为空、类型转换异常 | 元数据字段类型、加载字段、运行时对象样本 | 核对 select 字段、分录层级和空值分支 | UI 展示值不能替代 DynamicObject 类型证据 |
| F7/过滤连续出现 `bigint = varchar`、`Long cannot be cast to String` | 实体字段原始类型/引用属性、过滤列、`entityField` 模式、默认值和最终操作数 | 先建立四方类型合同，再改配置或 QFilter | 第一次类型错误后未读完整栈与标准元数据样本时停止猜测切换 |
| 操作成功但数据未变化 | 操作结果、事务边界、状态机、权限和回写链 | 区分执行状态、物理数据状态和异步所有权 | 只看到 `success=true` 时不能断言业务完成 |
| 页面/列表无数据 | 同一 traceId 下的入口参数、过滤、权限和最终查询 | 按过滤链逐层归因 | 不把并发超时或后台日志直接当根因 |
| MQ 重复、积压或丢失 | 业务幂等键、ACK 分类、重试台账、queue 配置 | 按 `cache-mq-runtime.md` 核对状态机 | 未分类异常被 `discard` 时先视为高风险 |
| 缓存脏读或击穿 | key/TTL/region、失效路径、锁和回源次数 | 按 `cache-mq-runtime.md` 核对一致性 | 缺少失效契约时不能用加长 TTL 代替修复 |

## 代码复核顺序

1. 先确认实现是否挂在正确入口、基类和事件点；不要从类名推断运行链路。
2. 再核对 SDK/元数据事实：方法签名、字段类型、加载字段、实体与操作编码。
   - 过滤/F7 同时记录：实体字段原始类型及引用属性、过滤列类型和 `entityField` 模式、默认值运行时类型、最终 QFilter 两侧操作数类型。四者未闭合时不能靠 Long/String 来回试错。
3. 再核对业务状态机和事务边界：成功、失败、重试、补偿、幂等和异步最终状态。
4. 最后检查资源与性能：`DataSet`、流、锁、MQ publisher、分页、循环内远程/数据库/cache 调用。

## 必报 findings

- 未检查空结果或未知状态。
- 循环内数据库、缓存或远程调用。
- 拼接用户输入到 SQL/KSQL、URL 或脚本。
- 保存/提交/审核绕过平台标准服务。
- MQ 未知异常直接丢弃、使用 `messageId`/`resend` 代替业务幂等。
- Cache 无 TTL/失效策略、无隔离 key、缓存无界集合。
- 捕获异常后只记 message、吞异常、返回成功或丢失 traceId。
- 只凭社区文章、项目片段或旧版本示例确认平台 API。

输出 finding 时给出文件/事件点、触发条件、影响、证据等级、最小修复和验证方式；静态证据与目标环境验证分开陈述。
