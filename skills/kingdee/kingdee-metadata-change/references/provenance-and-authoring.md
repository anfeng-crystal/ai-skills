# 元数据血缘门禁

## 为什么先判定血缘

输入文件存在、名称像原包、能解析或来自上一会话，都不能证明它是原始基线。历史 agent 修改包再次被当作基线，会把未经授权节点和错误身份继续传播；本 skill 必须在任何写入前阻断这一点。

## 每个文件记录

- 绝对路径和 SHA-256；
- 环境、平台版本、导出时间和导出人/方式；
- 导出类型、选中资源、安装目标与包产品版本；平台导出血缘本身不证明安装入口或跨版本兼容性；
- 直接父产物及其哈希；
- 是否经 agent、脚本、设计器保存、导入或重打包；
- 是否完成“导入—设计器打开保存—重新导出”对账；
- 证据来源，而不是推断。

合同只接受三种基线分类：

| classification | 资格 |
|---|---|
| `platform-exported` | 目标环境直接导出，有环境和时间证据 |
| `user-confirmed-original` | 用户明确确认未被 agent/脚本修改，并说明来源 |
| `repository-canonical` | 版本库规范源，有平台回导或发布血缘 |

`ai-derived`、`derived-candidate`、`unknown`、历史修复包和仅静态通过的包均不可冒充新的原始基线。允许在本轮候选上持续修正，但应保留可信原包、完整累计差异和候选哈希，验证始终追溯原包。用户明确指出某包是先前会话修改物时，立即把此前基于它作出的“原包”判断作废。

## 继续已导入的版本

1. 核对目标环境、对象、最近成功导入或验收的本地包，以及能确认包身份的 SHA-256 或导入记录。按本次影响范围比对目标端版本、相关节点和独立资源引用。表单版本一致时，仍需查看本次会随包导入的页面脚本、语言侧文件等独立资源是否完整。
2. 已验证包可作为本次编辑起点。沿用其可信原包和累计差异，单独核对本轮变更、引用及审计属性。只要目标未发现相关漂移且依赖完整，就沿用本地包和现有证据，无需重导出或额外在设计器保存。静态检查或相同文件名不能单独建立这一血缘。
3. 确认有在线变更、包缺少相关现行资源、缺少目标版本证据，或需要平台生成身份和关联时，先补读可定位的定义。需要导出时只取相应对象和资源，逐成员比对现行版本与候选，保留已有的用户改动。覆盖最终文件前核对待替换包与导入验收记录，同时保留可信原包供回滚。

## 污染处理

若只有派生包：

1. 只运行 `inspect` 和只读差异分析；
2. 将差异标为 `approved-business/platform-generated/legacy-valid/agent-derived/unexplained`；
3. 不自动保留或删除 `agent-derived/unexplained`；
4. 取得可信导出，或由用户明确指定原始版本；
5. 重新生成合同，旧候选和旧批准不沿用。

“标准模板没有该节点”只证明它不是标准定义，不能单独证明业务节点应删除。删除还需用户授权、来源和引用检查。

## 写入边界

- 修改已有标量属性可以走精确字节补丁，但必须命中可信基线、唯一节点和实际合同。
- 新字段、控件、操作、规则、插件节点和多语言行优先按 [本地新增](local-addition.md) 在本地构造；结构和身份生成依据、静态结果与平台验证状态分别记录。
- 不沿用模板或另一业务对象的独立身份；业务编码重新分配，继承身份和父容器等引用按目标对象实际关系解析。
- 不把继承节点完整物化到子层；恢复继承只移除真实差量覆盖。
- 本地候选、DEV/TEST 导入、生产导入和发布分别核对授权范围；同一条用户指令或同一已批准方案可以明确授权多个阶段。已覆盖阶段连续执行并验证，不逐阶段重复确认；未覆盖阶段先完成全部已授权准备，再询问。候选完成后返回主任务继续已授权工作，不以候选生成代替平台验证或整体完成。

## 平台导出与安装入口

官方[二开安装包制作](https://vip.kingdee.com/knowledge/specialDetail/218022218066869248?category=475348205593507584&id=43334364940533760&type=Knowledge&productLineId=29&lang=zh-CN)（更新于 2026-07-30，未标最低版本）区分补丁方式导出与普通导出：前者用于 MC 升级并有产品版本校验，后者用于开发者门户导入，不能据包扩展名混用安装入口。该说明只覆盖二开安装包，不可套到 DTS、工作流或单对象导出。记录目标版本、实际包类型和安装入口后再判定可用路径；本 skill 的离线候选、身份和授权门禁不因此改变。

## 修改审计属性

- 每次业务内容发生变更，包括上一候选的修订，都更新受影响设计单元的修改人和修改时间。平台在线保存后，复核并沿用平台实际记录。离线改包先用同环境的登录上下文、项目账号配置或用户确认，唯一定位本次操作人的平台用户 ID。读取和匹配所需信息即可，不回显凭据或以原包修改人、其他环境账号、系统管理员代填。无法唯一定位时，说明具体缺口，继续完成可独立核验的业务改动。
- 只更新同版本原生包已支持的审计属性，按实际路径、类型和单位写入。例如树形基础资料普通导出中，表单设计含 `ModifierId` 和 `ModifyDate`，实体设计含 `ModifyDate`，相关 `Version` 位于各设计单元及主包、语言侧包的外层。记录本次修改时刻，按原生关联关系同步已变更对象的版本戳。原格式未序列化修改人的单元不新增未知属性；业务节点身份、语言关联键和产品版本按原合同保留。
- 最终包逐路径核对修改人、修改时间、版本和业务差异。若现有结构验证器尚未覆盖审计差异，可在校验副本中精确还原审计属性以运行原验证器，并独立校验实际交付包的审计属性与其余内容的等价性。交付时报告当前修订改了什么、修改人、修改时间及验证层级。

## 验证层级

1. 静态：哈希、成员、XML、合同、精确差异；
2. 平台：核对逐对象导入结果并从目标设计器重开。平台保存与回导取证按交付要求或待验证结构执行；
3. 运行：真实菜单/首页入口及业务场景；
4. 生产：发布、缓存、回归和回滚。

只完成前一层不能用后一层措辞。正式交付可保留已核对导入和运行结果的本地最终包。需要平台原生保存产物时，按[原生对照与导出](native-designer-check.md)核对回导包的保存记录、版本和语言包关联。保留原包用于回滚。
